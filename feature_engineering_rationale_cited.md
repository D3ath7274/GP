## Abstract

This document provides a systematic justification for the ten feature groups selected for the behavioral network traffic dataset generated by the SDN-based IoT Intrusion Prevention System. For each feature group, the document articulates the specific attack mechanism that the features are designed to expose, explains the mathematical and network-theoretic basis for the chosen metrics, and explicitly addresses why simpler or more commonly used alternatives were insufficient for the threat model under consideration.

The discussion is grounded in the specific architectural constraints of the system — namely, an OpenFlow 1.0 software-defined network mirroring all data-plane traffic to a Ryu controller — and addresses the unique challenges introduced by the Mininet-WiFi emulation environment, including broadcast amplification artifacts and the absence of physical propagation delay.

The paper concludes that the chosen feature set provides multi-scale behavioral visibility spanning flow-level mechanics, device-level historical profiling, network-level entropy, and protocol-specific behavioral fingerprints, and that this combination is both necessary and sufficient for training a deep learning model capable of detecting not only known attack patterns but behavioral anomalies consistent with previously unseen attack variants.

**Index Terms:** Software-Defined Networking, Intrusion Detection Systems, Feature Engineering, Behavioral Profiling, Shannon Entropy, Network Anomaly Detection, Deep Learning, IoT Security.

## I. Introduction

The construction of a labeled network traffic dataset for machine learning is not a neutral engineering task. The choice of which packet attributes to measure, how to aggregate them across time windows, and how to represent device history constitutes a set of implicit hypotheses about what network attacks look like at the feature level. A dataset built on the wrong hypotheses will train a model that learns to recognize the specific tools used during data collection — hping3, nmap, arpspoof — rather than the underlying behavioral principles that make those tools detectable.

Such a model will fail the moment an attacker uses a different tool, a different rate, or a different payload pattern. This observation is well-established in the intrusion detection literature: benchmark datasets have repeatedly been criticized for training models that learn tool-specific artifacts rather than genuine attack semantics [8][9].

This document presents the reasoning behind each of the ten feature groups incorporated into the enhanced dataset schema. The goal is not to enumerate the features themselves — that documentation exists in the system's codebase — but to explain why those particular measurements were chosen over the many plausible alternatives, and why the alternatives were rejected.

The analysis is organized as follows. Section II describes the architectural constraints that shaped feature selection. Sections III through XII each address one feature group in detail. Section XIII compares the resulting feature set against established benchmark datasets. Section XIV concludes with a synthesis of the design philosophy.

## II. Architectural Constraints on Feature Design

Before motivating individual feature choices, it is necessary to establish the environmental constraints that ruled out certain otherwise attractive approaches.

### A. The Controller as a Passive Observer

The system operates a Ryu SDN controller that receives a full mirror of every data-plane packet via the OpenFlow `OFPP_CONTROLLER` action with `max_len=0xffff`. This means the controller observes the complete packet stream — headers and payloads — for every flow. This is an unusually privileged vantage point compared to, for example, a NetFlow-based sensor that receives pre-aggregated statistics from a hardware router.

The consequence for feature design is that per-packet granularity is available but not free: each packet triggers a Python function call, and the computational budget for feature accumulation is bounded by the packet arrival rate.

This constraint ruled out features that require deep packet inspection of application-layer payloads, such as HTTP method distribution or DNS query content analysis. While such features have strong discriminative power, extracting them at 150,000 packets per second in a single-threaded Python process would cause the controller queue to saturate before the attack data could be recorded. The feature set was therefore restricted to transport-layer and network-layer header fields, plus aggregate statistics derivable from those fields within a constant memory budget per flow. This design philosophy aligns with the flow-based feature extraction methodology employed in benchmark datasets such as CIC-IDS2017 [8] and UNSW-NB15 [9].

### B. The Mininet-WiFi Amplification Problem

The data plane is emulated by Mininet-WiFi, which introduces a non-trivial measurement artifact: every packet is processed by the OpenFlow software switch and mirrored to the controller twice — once through the switch's data path and once through the TAP interface clone. This doubles all raw packet counts and byte counts relative to what a physical sensor would observe.

This constraint ruled out any feature whose validity depends on absolute packet counts being accurate physical measurements. Features expressed as ratios — such as the ratio of SYN packets to ACK packets as defined in the TCP specification [1][2], or the ratio of forward traffic to backward traffic — are immune to this amplification because the numerator and denominator are inflated by the same factor. Features expressed as entropies of frequency distributions [5][6] are similarly immune because the relative frequencies are preserved under uniform scaling.

Raw PPS values, however, are inflated by a factor of approximately two and must be interpreted in that context. The threshold values in the detection engine (15,000 packets per window for ICMP floods, 5,000 for SYN floods) have been calibrated to account for this amplification.

### C. The Five-Second Window Constraint

All features are computed per five-second aggregation window per source IP. This temporal granularity is a design choice with significant implications:

- A **shorter window** (e.g., one second) would capture finer temporal dynamics but would produce fewer packets per window for low-rate normal traffic, making many statistical features unreliable due to small sample sizes.
- A **longer window** (e.g., thirty seconds) would smooth out the distinction between a brief spike and a sustained attack, compromising the consecutive-window confirmation system.

Five seconds was selected as the minimum window duration at which a flood attack produces enough packets to populate all statistical features reliably, while still being short enough to confirm a sustained attack within fifteen seconds. This window granularity is consistent with the flow aggregation intervals used in prior anomaly detection research [4][5].

This constraint ruled out session-level features that require observing the complete lifecycle of a TCP connection [1][2], since a single connection may span many five-second windows. Session completeness features are therefore computed as approximations within the window boundary rather than as exact measurements of individual connection lifecycles.

## III. Timing and Inter-Arrival Rhythm Features

### A. The Core Hypothesis

The fundamental hypothesis motivating this feature group is that human-generated network traffic and tool-generated attack traffic differ not only in volume but in **temporal regularity**. A user browsing the web generates packets at intervals shaped by human reaction time, server processing delay, and network propagation — intervals that are highly irregular and follow a heavy-tailed distribution [7]. A flood tool running on modern hardware generates packets at intervals constrained only by the operating system's network stack and the CPU clock, producing an interval distribution that is extremely narrow and concentrated near a single value [7][8].

This hypothesis is operationalized through the **coefficient of variation of inter-arrival times**, defined as the ratio of the standard deviation to the mean of the inter-arrival time series [8]. A coefficient of variation near zero indicates robotic regularity; a coefficient of variation substantially greater than zero indicates the natural irregularity of human-initiated or application-driven traffic. Crucially, this metric is sensitive to attack behavior regardless of the attack's volume — a slow-rate flood at 100 PPS is just as temporally regular as a high-rate flood at 100,000 PPS [7][8].

### B. Why Not Use PPS Alone

The most common approach in threshold-based intrusion detection systems is to trigger an alert when the packets-per-second rate from a given source exceeds a fixed threshold [4]. This approach has a well-known failure mode: the threshold must be set high enough to avoid false positives during legitimate high-volume traffic (such as iperf throughput tests), but setting it high also means that moderate-rate attacks — those deliberately kept below the threshold — go undetected.

More fundamentally, PPS is a scalar quantity that discards all temporal structure. Two flows with identical mean PPS can have radically different inter-arrival distributions: one perfectly uniform (attack tool) and one highly irregular (legitimate application). The inter-arrival coefficient of variation captures this distinction; PPS alone cannot [7][8].

### C. Why Not Use Payload Content for Timing

An alternative approach is to infer attack timing from application-layer content — for example, by observing that all HTTP requests have identical User-Agent strings or that all DNS queries are for the same domain. While such features have high precision for known attack tools, they require deep packet inspection, which is computationally expensive and fails entirely against encrypted traffic.

Transport-layer timing features require only the arrival timestamp of each packet, which is available at zero additional parsing cost in the controller's `packet_in` handler. This approach is consistent with the header-only feature extraction philosophy established in landmark anomaly detection work [4][5].

### D. The Burst Detection Rationale

The `burst_count` and `burst_duration_avg` features address a specific attack variant not captured by the coefficient of variation: **pulsed attacks** that alternate between periods of very high rate and brief pauses. Such attacks are sometimes used to evade window-based rate counters that measure average PPS over the full window — the pauses bring the average below the threshold even though the peak rate during bursts is clearly malicious.

Burst detection identifies periods within the window where the instantaneous rate exceeds three times the window mean (a threshold selected based on the observation that legitimate traffic spikes rarely exceed twice the mean sustained rate), counting how many such periods occurred and how long they lasted on average. An attack conducting ten bursts of 500ms each per five-second window will have a `burst_count` of ten and a `burst_duration_avg` of 0.5, while a legitimate high-throughput flow will have a `burst_count` near zero.

## IV. Directionality and Asymmetry Features

### A. The Asymmetry Principle

Network attacks directed at a target host are, by definition, asymmetric: the attacker transmits large volumes of traffic toward the victim, and the victim either fails to respond (due to resource exhaustion) or responds minimally. This asymmetry is one of the most universal properties of volumetric attacks — it holds for ICMP floods, SYN floods, UDP floods, and port scans regardless of their specific implementation [4][5].

The forward-to-backward packet ratio and forward-to-backward bytes ratio quantify this asymmetry directly. For legitimate bidirectional communication — a TCP file transfer, an HTTP session, a VoIP call — both ratios hover near 1.0 or at a modest imbalance reflecting the underlying protocol semantics as defined in the TCP specification [1][2]. For a flood attack, the forward ratio approaches infinity as backward traffic goes to zero.

### B. Why Not Use Connection State Tables

A stateful firewall approach to detecting asymmetry would maintain a connection state table and flag connections where responses are absent after a timeout. This approach is standard in enterprise firewalls but is unsuitable here for two reasons:

1. Maintaining per-connection state at 150,000 PPS generates memory pressure proportional to the number of concurrent half-open connections, which is exactly what a SYN flood maximizes — a well-known vulnerability of stateful inspection systems [1][2].
2. The five-second window model is fundamentally stateless — state resets at each window boundary. The directionality ratios are computed within the window without any cross-window connection tracking, providing asymmetry information at constant memory cost regardless of flood intensity.

### C. The Reply Rate as a Victim Responsiveness Signal

The `reply_rate` feature estimates what fraction of outgoing packets received a response within the same five-second window. For normal application traffic to a functioning server, the reply rate should be close to 1.0 for connection-oriented protocols, because by definition of the TCP acknowledgment mechanism every successfully delivered segment generates a corresponding ACK [1][2].

A low reply rate from a destination that is normally responsive therefore indicates either that the destination is overwhelmed and dropping packets or that the source is sending to closed ports or non-existent hosts — both of which are consistent with attack behavior [5].

## V. TCP Session Completeness Features

### A. The Protocol Contract Violation Model

The TCP protocol specifies a well-defined lifecycle for every connection: a three-way handshake (SYN → SYN-ACK → ACK) establishes the connection, data transfer follows, and a FIN sequence terminates it cleanly, with RST available for abnormal termination [1][2]. Legitimate TCP applications overwhelmingly follow this contract. Attack tools, by contrast, are specifically designed to violate it:

- SYN flood tools send only the SYN packet and never complete the handshake.
- Port scan tools probe ports and immediately move on, generating RST responses without establishing connections.
- TCP RST flood tools send only RST packets.

The SYN-to-ACK ratio, incomplete session ratio, and FIN count features operationalize this protocol contract as measurable quantities. They require no knowledge of what application is running or what data is being transferred — they measure only whether the session lifecycle conforms to the TCP specification [1][2].

### B. Why These Flags Rather Than Others

TCP has six flag bits: URG, ACK, PSH, RST, SYN, FIN [1]. The PSH flag indicates that the sending application has data to push immediately and is common in legitimate interactive traffic (SSH, Telnet). The URG flag is rare in normal traffic and extremely rare in attack traffic as well, making it a weak discriminator in either direction.

This feature group focuses on SYN, ACK, FIN, and RST because these four flags encode the **session lifecycle state machine** — the full grammar of which connections are being opened, completed, and terminated — while PSH and URG encode application-layer urgency signals that are irrelevant to session completeness analysis [1][2].

### C. The Incompleteness Ratio as a Zero-Day Indicator

Among the session completeness features, the **incomplete session ratio** deserves particular attention as a potential zero-day attack indicator. Any network behavior that generates large numbers of half-open sessions — SYN floods being the canonical example — will produce a high incompleteness ratio regardless of what specific tool generated them [4][5].

A novel attack tool not in the Snort signature database and not previously seen during training will still produce this feature value if it uses the same attack category. The incompleteness ratio is therefore a **category-level indicator** rather than a tool-level indicator, which is precisely what is needed for generalization beyond the training distribution [8][9].

## VI. Shannon Entropy Features

### A. Information Theory as a Traffic Diversity Metric

Shannon entropy, borrowed from information theory [6], measures the diversity or unpredictability of a distribution. Applied to network traffic, entropy quantifies how diversely a host is distributing its traffic across ports, destinations, or packet sizes [4][5].

Flood attacks produce near-zero entropy in the dimension they are targeting:
- An ICMP flood generates all type-8 packets [3] → entropy ≈ 0 for ICMP type distribution
- A UDP flood targets a single port → entropy ≈ 0 for destination port distribution
- A port scan generates uniformly distributed destination port values → entropy = maximum [5]

These extreme values are a direct consequence of what the attack is trying to achieve — overwhelming a specific resource — and not an artifact of the specific tool used.

### B. Why Entropy Rather Than Raw Counts

The naive alternative to entropy is to count unique values: unique destination ports contacted, unique ICMP types seen. Counting unique values provides some discriminative power, but it discards distributional information. A host that contacts 100 ports, with 99% of packets going to port 80 and 1% distributed across 99 others, has `unique_dst_ports = 100` but entropy near zero because the distribution is dominated by a single value. Entropy captures this concentration in a single scalar, and its mathematical properties make it directly interpretable as a diversity measure [6].

Lakhina et al. demonstrated empirically that entropy of traffic feature distributions enables the detection of a substantially wider class of anomalies than volume-based metrics alone, including many classes of attack that produce no measurable change in total traffic volume but do collapse the diversity of port or address distributions [5].

### C. The Multi-Dimensional Entropy Design

Four entropy features are computed over different dimensions of the traffic:

| Feature | What it captures |
|---|---|
| Destination port entropy | Flood vs. scan distinction |
| Payload size entropy | Uniform-size attack tools vs. variable-size application traffic |
| Source port entropy | Random source port spoofing used in some flood tools |
| ICMP type code entropy | ICMP flood vs. normal ICMP (RFC 792 [3]) |

Computing entropy over multiple dimensions is necessary because no single dimension is universally discriminative. A UDP flood can use random source ports — appearing diverse in the source port dimension — while remaining maximally concentrated in the destination port dimension. This multi-dimensional approach is directly motivated by the framework of Lakhina et al. [5].

### D. Why Not Use Statistical Variance Instead

Variance is another measure of spread that could serve a similar role. Entropy was preferred for port distributions because port numbers are **categorical identifiers, not numeric quantities** whose magnitude carries meaning. Treating port numbers as integers and computing their variance would produce a high value for a scan across a wide port range (ports 1–65535) but an artificially low value for a scan targeting only low-numbered ports (ports 1–100), even though both are equally concentrated attack behaviors. Entropy treats port identifiers as categories and is therefore invariant to the numeric magnitude of the port numbers [5].

## VII. ARP-Specific Behavioral Features

### A. The Visibility Gap in Generic Flow Features

ARP spoofing is fundamentally different from the volumetric attacks addressed by the previous feature groups. It does not generate high packet rates, it does not create port diversity, and it does not violate TCP session lifecycle rules [1][2]. A network under ARP spoofing attack may exhibit perfectly normal traffic rates, normal session completion patterns, and normal entropy across all port dimensions — because the attack operates at Layer 2 by poisoning the ARP cache, not by generating anomalous IP traffic.

Generic flow features computed over IP packets are structurally incapable of detecting ARP spoofing because ARP operates below the IP layer and outside the scope of IP flow analysis.

This gap motivated the dedicated ARP feature group. Without it, ARP spoofing would be detectable only through Snort signature matching (Tier 1 of the detection engine), with no behavioral profiling fallback. This is a known weakness of existing benchmark datasets — both CIC-IDS2017 [8] and UNSW-NB15 [9] do not include dedicated ARP feature groups.

### B. The Unsolicited Reply Signal

The most discriminative single feature in this group is the **unsolicited ARP reply count** — the number of ARP replies sent by a host that were not preceded by an ARP request from the target host within the observation window. Legitimate ARP replies are responses to specific ARP requests; a host that generates replies without being asked is almost certainly poisoning the cache of other hosts.

This asymmetry between ARP requests and replies has no benign explanation at significant volumes. A small number of gratuitous ARPs (where a host announces its own IP-to-MAC mapping) is normal during device startup, but a sustained stream of unsolicited replies targeting another host's IP-to-MAC binding is the defining signature of an active spoofing attack.

### C. The Persistent Binding Table Requirement

MAC-to-IP binding change tracking requires state that persists across five-second windows — a legitimate device rarely claims different IP addresses, so a binding change detected today is still meaningful tomorrow. This is handled through a module-level dictionary (`_mac_to_ip_history`) that accumulates all IP addresses a given MAC has claimed since the controller started.

The alternative — tracking binding changes only within each five-second window — would fail to detect **slow ARP poisoning** where the attacker gradually shifts the binding over many windows, keeping the per-window change count below any reasonable threshold. The persistent binding table approach is immune to this evasion because the historical record grows monotonically; any deviation from a device's established binding pattern is visible regardless of how slowly it occurs [4].

## VIII. Packet Size Distribution Features

### A. The Uniformity Signature of Attack Tools

Commercial and open-source flood tools generate packets of fixed or configurable size. hping3, for example, generates ICMP packets of 28 bytes by default (the minimum ICMP echo request as defined in RFC 792 [3]), with the payload size controllable via the `-d` flag. The packets generated in a single flood session are all identical in size — the **standard deviation of packet sizes in an attack flow is therefore near zero**.

Legitimate application traffic, by contrast, is highly variable in packet size because different application events (small acknowledgments, large data segments, retransmissions) produce packets of different sizes. A file transfer using TCP generates packets ranging from 40-byte acknowledgments to 1460-byte maximum segment size data packets [1][2]. Lakhina et al. identified payload size distribution as one of the key feature dimensions whose entropy collapses during attack traffic [5].

### B. Why Standard Deviation Rather Than Min-Max Range

The range (`max_size − min_size`) might seem sufficient to capture size variability — a flow with only 28-byte packets has range = 0. However, range is highly sensitive to outliers and does not capture the distribution of sizes across all packets. A flood tool that occasionally sends one large packet to probe a maximum transmission unit will have a non-zero range even if 99.9% of its packets are identical in size.

Standard deviation weighs all packets equally and is resistant to this manipulation. The `packet_size_variance` feature is derived from the standard deviation and serves as an additional input for the deep learning model. The use of variance as a secondary feature alongside standard deviation is consistent with the multi-statistic approach in the IDS literature [8][9].

### C. The Small and Large Packet Ratio Features

The `small_packet_ratio` (fraction of packets under 100 bytes) and `large_packet_ratio` (fraction of packets over 1000 bytes) complement the standard deviation by providing interpretable boundary statistics:

- **SYN flood packets** are always small — the SYN packet has no data payload and typically spans 60–74 bytes depending on TCP options present, derivable from the 20-byte minimum TCP header and 20-byte IP header specified in RFC 793 [1].
- **UDP amplification attack responses** are always large — the amplification factor depends on the response being substantially larger than the request.

These ratios directly encode the known physical characteristics of specific attack categories in a form that a neural network can associate with labels during training [8].

## IX. Port Behavior Features

### A. Distinguishing Floods from Scans at the Port Level

Flood attacks and port scans occupy opposite extremes of the destination port diversity spectrum:

- A **flood attack** typically directs all traffic to a single destination port → destination port standard deviation ≈ 0, top port ratio ≈ 1.0
- A **port scan** contacts as many distinct ports as possible → high destination port standard deviation, top port ratio ≈ 0

The entropy features in Section VI capture these extremes in the frequency domain [5][6]; the port behavior features in this section capture the same extremes in the magnitude and ordering domains, providing complementary signal.

The existing `unique_dst_ports` count captures the number of distinct ports but not their distributional properties. The standard deviation of destination port numbers, the top port ratio, and the sequential port score together provide a complete characterization of both the concentration and the ordering pattern of port usage.

### B. The Sequential Port Score and Its Specificity

The sequential port score — the fraction of consecutive port pairs in the observed sequence where the second port is within two of the first — is specifically designed to detect the default scanning behavior of nmap, which probes ports in sequential order unless randomization is explicitly requested.

The justification for including tool-specific features alongside general behavioral features: while the deep learning model should generalize beyond specific tools, its training data is necessarily generated by specific tools. Including features that are highly discriminative for the tools used during training — alongside features that capture general behavioral principles [4][5] — gives the model both a strong training signal and the general features needed for generalization. A model trained with only general features may fail to converge; a model trained with only tool-specific features will overfit [8][9].

### C. Well-Known and Ephemeral Port Ratios

- **Well-known ports (0–1023)** host standard services — HTTP on 80, SSH on 22, DNS on 53, SMTP on 25.
- **Ephemeral ports (49152–65535)** are dynamically assigned by the OS to outgoing connections.

A host directing nearly all traffic to well-known ports is likely engaging in service-targeted activity — which could be legitimate or malicious (a targeted flood or service exploitation attempt). These ratios provide context for the port entropy [5][6] and standard deviation features without adding computational complexity.

## X. Broadcast and Multicast Environment Features

### A. The Mininet-Specific False Positive Problem

The broadcast and multicast features address a challenge unique to the Mininet emulation environment. During a `pingall` operation in Mininet — a diagnostic command that sends ICMP echo requests between all host pairs — the software switch generates broadcast ARP storms as it learns the network topology. These storms can produce several thousand packets within a single five-second window from a single source, with:

- Near-zero inter-arrival coefficient of variation [7][8] (the broadcasts arrive in rapid succession)
- Near-unity top destination ratio (broadcast address)
- High ICMP rate

In the absence of broadcast-specific features, these legitimate operational events are indistinguishable from a real ICMP flood at the feature level. The `broadcast_ratio`, `multicast_ratio`, and `ARP_broadcast_ratio` features give the deep learning model a direct signal for classifying broadcast-storm windows as normal rather than requiring the model to infer this from the elevated threshold alone.

### B. Why These Features Are Environment-Specific but Necessary

A critic might argue that environment-specific features reduce the generalizability of the dataset and the model trained on it. This argument would be valid if the goal were to produce a general-purpose IDS dataset comparable to CIC-IDS2017 [8] or UNSW-NB15 [9]. The goal here is different: to train a model that operates specifically within this SDN topology, with this controller architecture, on this emulated network. **A model that achieves 99% accuracy in the lab but generates constant false alarms during routine `pingall` operations is operationally worthless.**

Furthermore, real networks also generate broadcast traffic during normal operation — ARP resolution, DHCP discovery, Spanning Tree Protocol convergence. A model trained to recognize broadcast context as a normal signal will generalize correctly to physical deployments; a model trained without this context will generate false alarms whenever the physical network undergoes routine broadcast activity.

## XI. Flow-Level Context and Device History Features

### A. The Baseline Maturity Signal

The Z-score deviation features in the device behavioral profile (`device_pkt_rate_deviation`, `device_byte_rate_deviation`, `device_payload_size_deviation`) compare each window's traffic against the device's historical average using Welford's online algorithm. These features are powerful for detecting behavioral changes [4] but have a well-known **cold-start problem**: during the first 180 seconds of a device's lifetime in the network, the historical average is based on too few observations to be statistically reliable.

The `is_baseline_mature` binary flag encodes exactly when the historical baseline becomes reliable — after 20 observed flows and 180 seconds (thresholds selected to balance stabilization speed against detection responsiveness). Including this flag in the feature set allows the deep learning model to learn a conditional behavior:

- When `is_baseline_mature = 1`: apply Z-score deviation features with full weight.
- When `is_baseline_mature = 0`: treat them with skepticism.

Without this flag, the model must infer this conditional from `device_total_flows` and `device_age_seconds`, requiring the model to learn the threshold values from data rather than having them directly encoded.

### B. The Flows Per Window Feature and Connection Flooding

The `flows_per_window` feature counts how many distinct flow entries a source IP generated within a single five-second window. This feature is specifically designed to detect **connection flooding** — an attack where the goal is not to generate high packet volume to a single destination but to open as many simultaneous connections as possible, exhausting the target's connection table.

Connection flooding attacks can appear benign in all rate-based and entropy features [5][6] because each individual flow has low packet count and unremarkable timing characteristics. Only the aggregate number of flows from a single source reveals the anomaly.

This feature also distinguishes network scanning from port scanning:
- A **port scan** generates high `unique_dst_ports` from a single source to a single destination.
- A **network scan** generates high `flows_per_window` because each probed IP address constitutes a separate flow entry. The `flows_per_window` feature captures the horizontal scan pattern (one source, many destinations) that `unique_dst_ports` misses.

## XII. Metadata Columns and Their Role in Dataset Integrity

### A. The Distinction Between Features and Metadata

The metadata columns (`meta_attack_tool`, `meta_attack_intensity`, `meta_mininet_event`, `meta_session_id`, and others) are **explicitly excluded from the training feature set**. They serve a different function: they provide ground-truth annotations about the experimental conditions under which each row was generated.

This distinction is critical because the metadata columns would constitute **data leakage** if included as model inputs — a model trained with `meta_attack_tool` as a feature would learn to predict labels directly from the tool identifier rather than from the behavioral features, producing artificially high training accuracy and zero generalization to real deployments. This data leakage problem is a documented pitfall in the IDS dataset literature [8][9].

### B. The Reproducibility Function

The metadata columns serve two reproducibility functions:

1. **Post-hoc validation:** By filtering on `meta_attack_tool = hping3` and verifying that all such rows have non-zero label values, one can confirm that the `ATTACK_START`/`ATTACK_STOP` metadata signaling was working correctly during data collection.
2. **Ablation studies:** By filtering on `meta_mininet_event = pingall` and examining the feature distributions, one can verify that the broadcast-related features correctly distinguish `pingall` windows from genuine flood windows. The provision of such metadata is recommended in the IDS dataset evaluation framework literature [8].

### C. The Controller Load Features

The `meta_controller_load` column records the processing latency per flush — the time required to compute all features for one five-second window. This metadata is valuable for understanding the computational limits of the system under attack conditions: a sustained 150,000 PPS flood may push the feature computation time well above the five-second window duration, causing windows to back up. If `meta_controller_load` values show window computation times exceeding 5,000 milliseconds during flood attacks, the feature set should be profiled and optimized before deployment.

| Directionality & asymmetry | ✓ 7 features | ✓ Fwd/Bwd split | ✓ Partial |
| TCP session completeness | ✓ 4 features | ✓ Flag counts only | ✓ Flag counts only |
| Shannon entropy (multi-dim) | ✓ 4 features | ✗ Not present | ✓ 2 features |

| Packet size distribution | ✓ 4 features | ✓ Partial | ✓ Partial |

| Device behavioral history | ✓ 16 features | ✗ Not present | ✗ Not present |
| **Total feature columns** | **~85+** | **78** | **49** |

Two feature groups are unique to this work and absent from both benchmark datasets:

1. **ARP-specific behavioral features** — absent from benchmarks because most benchmark datasets are generated on physical networks where ARP spoofing has a distinct network-layer signature, or because the benchmarks focus on network-level rather than host-level attack scenarios [8][9].
2. **Device behavioral history features** — absent because benchmark datasets are typically static snapshots rather than live systems with persistent per-device profiling.

The device behavioral history features are particularly significant for zero-day detection. CIC-IDS2017 [8] and UNSW-NB15 [9] train models on absolute feature values — the model learns that a specific PPS value is malicious. The device deviation features in this work train the model on **relative deviations from a device's own historical baseline** — the model learns that a significant departure from normal behavior is malicious, regardless of the absolute value. This distinction is the mathematical foundation for the claim that the system can detect behavioral anomalies consistent with previously unseen attack patterns [4][5].

## XIV. Conclusion

The feature set documented in this work was not selected by enumeration — by listing all plausible packet header fields and including them all — but by reasoning backward from the attack mechanisms under consideration to the measurements that expose those mechanisms most directly. Each feature group was motivated by a specific hypothesis about how attacks differ from normal traffic, each hypothesis was operationalized through a specific mathematical or statistical measure, and each alternative measure was evaluated and rejected based on its:

- Computational cost
- Sensitivity to the Mininet amplification artifact
- Dependence on attack-specific tool behavior
- Failure to generalize across attack intensity levels

The result is a feature set that operates at **three levels of abstraction simultaneously**:

1. **Flow level** — captures the mechanics of individual connections: their duration, volume, timing regularity [7][8], and protocol conformance [1][2].
2. **Device level** — captures behavioral history: how much a device's current behavior deviates from its own established baseline [4].
3. **Network level** — captures global state: the entropy of source IP distributions [5][6], the total active flow count, and the prevalence of broadcast traffic.

This multi-scale approach is necessary because different attack types manifest their anomalies at different scales.

The deep learning model trained on this dataset inherits the multi-scale structure of the features. Convolutional layers operating on flow-level features will learn local feature interactions — the relationship between `syn_count` and `ack_count` that signals a SYN flood [1][2]. Recurrent or attention-based layers operating on temporal sequences of windows from the same device will learn the temporal pattern of behavioral change that precedes and follows an attack. The combination provides detection capability at both the within-window and cross-window levels, which is the foundation for the system's intended zero-day detection capability [4][5][8][9].
