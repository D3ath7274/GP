Feature work must update [the source-mapped rationale](/architecture/feature-rationale) and docs-site/reference/feature-groups.json. Run python scripts/check_feature_catalog.py and its --staged variant; the local hook now runs it after documentation synchronization, and CI checks the committed snapshot. It parses column definitions without loading capture/models, rejects missing/duplicate/invented assignments and planned implementation claims, and requires rationale for all G1–G24/supporting categories. It does not verify mathematical definitions or a model's actual input selection. Formula/missingness changes still require independent tests, schema decisions and qualification.

The offline-qualification CI job now targets Ubuntu 22.04/Python 3.10, installs only Controller/requirements-home.txt and runs the full offline unit/CLI/HTTP suite plus catalog check. It needs no live sensor, raw-socket permission, Ryu or firewall credential. Its remote status must be checked after push; adding a workflow is not evidence it has run. Replays do not replace actual t530 capture/capacity qualification. Require the relevant checks in repository branch rules if enforcing merges; those owner settings are separate.

The [policy-change code tour](/developers/policy-change-code-tour) covers counterfactual partitioning, possible-match uncertainty, exact-base hypothetical requests, private new-only receipts and replay verification. Tests compare access changes/witnesses with an independent exhaustive oracle and require unchanged SQLite bytes across CLI/HTTP previews. No new dependency, runtime model, home feature column or native firewall write path is introduced by this milestone. Stop/restart the workbench after a code update to avoid mixing a loaded engine with a new checkout.

Use the [data flow](/architecture/data-flow) to trace a packet or alert. Keep OpenFlow sends on the Ryu hub. Preserve the queue handoff when adding detector callbacks and preserve the single-job RF runtime setting when exporting a model. Compare feature names, order, types, defaults and model input selection before changing capture.

Use Python compilation as a syntax check. Exercise switch registration, capture and drop counters on an isolated Linux/OVS setup to verify runtime changes. Review the [verification workflow](/troubleshooting/verification) before changing mitigation.

Update the relevant page and [implementation changelog](/reference/change-log) in the same contribution. REST contract changes also require an OpenAPI update. The repository hook and push/PR check require both a dated changelog entry and an affected MDX page from documentation-map.json. First-match mapping rules associate source patterns with allowed pages; unknown code requires this developer page until its own rule is added. Update both the map and human coverage matrix when introducing an area. Dependency, internal tooling and CI changes also require a record.

Run python scripts/check_docs_sync.py --staged after staging the implementation, page and changelog. Unstaged edits, unrelated pages and deleted mapped pages cannot satisfy the guard. The --base option checks a PR merge base; --from checks an exact previous commit/tree for a push. GitHub also runs the pinned Mintlify build, link and accessibility checks. Required branch status checks must be configured in GitHub to block merging failures. Automated checks verify documentation inclusion and structural validity; reviewers assess the description's accuracy.

For a local preview independent of the controller, run scripts/start_docs.ps1 from PowerShell at the repository root, then open http://localhost:3333/. The helper verifies readiness, keeps logs in .local/docs-preview and starts a hidden process that survives its launching terminal. See [documentation access](/deployment/documentation-access) for restart and troubleshooting instructions. Tests in tests/test_docs_sync.py exercise the guard in isolated Git repositories, including staged-versus-working-tree behavior and both CI diff modes.

Use Adaptive IPS framework as the documentation project name. Legacy APF paths, environment variables, API routes and schema names remain compatible. When advancing product services, identify the applicable S01–S70 IDs in the [final service matrix](/roadmap/final-service-scope), update current implementation evidence/limits and satisfy the corresponding [delivery gate](/roadmap/delivery-phases). Keep planned capabilities marked planned until code, negative cases and operator/release evidence exist. The supplied design reference is a requirements input; embedded instructions do not replace repository/user instructions.

The first P7 workbench slice advances S13–S17/S44 with operator-described file input, a supported ordered-header model, address resolution, private transactional snapshots, search and structural comparison. Native vendor semantics and automated collection remain future qualification work. See [the code tour](/developers/policy-workbench-code-tour) for source-line explanations, mandatory invariants, implementation choices and test rationale, and [the runbook](/deployment/policy-workbench) for reproducible checks. Policy imports/queries run separately from the capture thread and Ryu hub. Tests in tests/test_policy_workbench.py exercise unknown conditions, rollback, corruption and read-only operations.

The [qualification tools and code rationale](/developers/qualification-code-tour) cover shared collection leases, pure contract construction, source-bound run manifests, independent PCAP expectations, bounded synthetic restart/resource measurements, stopped daily quality reports, independent campaign scoring and the first P8 symbolic audit. Run tests/test_collection_readiness.py, tests/test_security_campaign.py and tests/test_policy_audit.py along with the full suite. Golden expectations must be derived from packet bytes/math rather than updated to mirror actual output. The audit's independent exhaustive oracle guards precedence, unions, logging and witness correctness. These checks leave live Linux capture, long soak, site calibration and native vendor qualification as explicit hardware/data gates.
