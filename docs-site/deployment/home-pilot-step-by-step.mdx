This revised procedure fits the reported t530: Ubuntu 22.04, Python 3.10, one active physical Ethernet interface enp1s0, no detected Wi-Fi interface, about 16 GiB free and a synchronized UTC clock. OVS/Docker interfaces are virtual; their presence does not add a second physical cable path. The old br-snort is not a source of current household traffic merely because it exists.

**Recommended topology: keep the ZTE as the Internet router, move household Wi-Fi to a separate bridged access point, and mirror the managed switch to the t530.** One t530 Ethernet interface is enough to receive copies. A wired switch can observe Wi-Fi clients' traffic when that traffic crosses the AP's Ethernet uplink. This recommendation is an engineering topology derived from those forwarding paths, not a claim that any untested router/switch firmware has the needed features.

An ordinary cable to a ZTE LAN port still does not create a mirror. Native LAN/WLAN mirroring on the ISP H188A firmware remains unverified. If you have no verified router mirror, managed switch/external AP or equivalent observation path yet, perform Session 1's offline checks only; do not start a supposed whole-home baseline. No command on enp1s0 can recover unicast frames the network never delivers to it.

**Current pause:** the H188A is still the actual household AP and no replacement/mirror path has been qualified. The topology below is an option, not an installed arrangement. Use [the offline implementation/testing lane](/deployment/offline-policy-changes) and [feature-group rationale](/architecture/feature-rationale) while resolving visibility. Model confidence, baseline approval and whole-home monitoring remain data/observation gated.

## Plan, equipment and wait times

| Session | Planned duration / wait | Exit condition |
| --- | --- | --- |
| 0. Select the topology and management method | 10–15 minutes; equipment acquisition is separate | Physical paths and single-port access limitations understood. |
| 1. Prepare the t530 while it has normal Internet access | 15–30 minutes; package/build time varies | Correct checkout, requirements and offline qualification work. |
| 2. Wire the switch and bridged AP | 20–40 minutes; allow 2–5 minutes per reboot | PC/phones have normal Internet through the intended paths. |
| 3. Enable ingress mirroring and test management | 10–15 minutes; 30 seconds for a link change | Mirror configuration saved; local console available; remote access either verified or explicitly unavailable. |
| 4. Test each phone against the wired PC | 60-second capture per phone, then review; about 10–15 minutes total | Successful phone fetch and matching packets in both directions on t530. |
| 5. Test Internet paths and address families | 60 seconds per device/family/path under test | Coverage and bypasses recorded; no hidden NAT aggregation. |
| 6. Header-only qualification | 10-minute timed capture plus 5–10 minutes review | Correct observations and no unresolved integrity problem. |
| 7. Optional metadata qualification | 20-minute timed capture plus review | DNS/TLS/HTTP settings and limitations understood. |
| 8. First operational run | 1 hour, inspect; then 24 hours, inspect | Resources, clock, visibility and closed-file quality remain acceptable. |
| 9. Representative collection | Initial 14 days, checked daily | Required workflows/devices represented, with a private activity ledger. |

These durations are practical test schedules, not mathematical accuracy guarantees. An AP reboot taking longer than five minutes needs investigation against its own manual; repeating waits does not fix incorrect cabling or mirroring.

Minimum equipment for the recommended path:

- A managed Gigabit switch with enough ports and **multiple source ports with ingress/RX-only mirroring** to one destination port. A product labeled merely unmanaged is insufficient. Verify the exact hardware revision and firmware's mirror controls before buying.
- A separate Ethernet-uplink access point, or a spare router that supports genuine AP/bridge operation without client NAT. A second ISP modem is not required. Appropriate security settings stay enabled; do not use an open SSID.
- Four Ethernet cables for ZTE–switch, AP–switch, PC–switch and t530–switch. A spare ordinary switch port is used for recovery/export. The five-port map below is sufficient; an eight-port switch leaves expansion room.
- A local display and keyboard on the t530 for setup/recovery unless an independent management path already exists.

TP-Link's [switch guide](https://static.tp-link.com/Easy%20Smart%20Switch_User%20Guide.pdf) describes source/destination and ingress/egress controls; its [older TL-SG108E guide](https://static.tp-link.com/resources/document/TL-SG108E_V1_UG.pdf) also shows revision-specific behavior. Those are examples of required functionality, not a guarantee of every current device's compatibility. Do not assume all products sharing part of a model name behave identically.

## Session 0 — Fix the observation topology

```text
Internet / DSL
      |
ZTE H188A: routing, DHCP and NAT remain here
      | LAN
      |                 Managed switch
      +---------------- P1: router link       [mirror source RX]
                        P2: bridged AP       [mirror source RX] ---- three phones on AP Wi-Fi
                        P3: wired PC         [mirror source RX]
                        P4: ordinary spare/recovery port
                        P5: mirror destination -------------------- t530 enp1s0
```

Connect each monitored wired endpoint through the observed switch. Move every monitored phone to the external AP's SSID. Keep the ZTE Wi-Fi available for rollback during migration; after validating the new AP, disable its radios or make all monitored devices forget its SSID so they cannot silently reconnect there. Phones left on the ZTE's built-in Wi-Fi bypass the AP uplink. Do not alter the ZTE's DSL/PPPoE/Internet credentials, routing or DHCP merely to install this passive pilot.

The AP must bridge clients to the existing LAN. In router/NAT mode, the switch might see only the AP's upstream address, undermining per-device profiles. Follow the AP vendor's documented mode and uplink-port instructions. If using a spare router's manual AP method, DHCP must not compete with the ZTE, and its management address must not conflict with the DHCP pool. [AP configuration reference](https://www.tp-link.com/us/support/faq/1384/)

### What this path covers

| Traffic | Expected visibility after verification |
| --- | --- |
| Phone to Internet and back through external AP | Crosses P2/P1; original client IPs are present on the LAN side before ZTE NAT. |
| Wired PC to Internet and back | Crosses P3/P1. |
| Phone to wired PC and back | Crosses P2/P3. |
| Two devices on different observed switch ports/APs | Their traversing frames can be mirrored. |
| Two phones communicating inside the same AP | May be switched locally and never reach P2. Do not claim lateral coverage without a separate test/observation design. |
| Phones still on ZTE Wi-Fi; devices locally communicating behind another unobserved switch | Bypass paths may be invisible. |
| Public probes rejected on the ZTE's WAN side | A LAN mirror may never receive them. |
| HTTPS/QUIC application payloads | Headers/limited visible metadata only; this is not decryption or Wi-Fi radio monitoring. |

The same-AP limitation follows local forwarding: see [Nokia's AP-local switching discussion](https://infocenter.alcatel-lucent.com/public/7750SR1910R1A/topic/com.sr.triple.play/html/vrgw.html). Later lateral-movement coverage may require separate VLANs/controlled inter-segment routing, AP/controller telemetry or a qualified AP capture facility. Client isolation blocks some traffic; it does not automatically export otherwise invisible traffic to this sensor. Do not add isolation/VLAN changes during the initial normal baseline without documenting their effect on household services.

### A single NIC must also have a management plan

Some mirror destinations are receive-only monitoring ports and stop ordinary networking. [Cisco's SPAN documentation](https://www.cisco.com/c/en/us/support/docs/switches/catalyst-6500-series-switches/10570-41.html) explicitly discusses analyzer reachability. Consequently, **capture support is not proof that SSH, dashboard access, updates or NTP will work through P5.** Choose one of these paths:

1. **One NIC with verified shared mirror/management behavior:** the exact switch/firmware explicitly supports ordinary bidirectional host connectivity on that mirror destination. Verify it while mirroring is active, including DHCP renewal/reboot, NTP, SSH and observation counts. Do not use an undocumented ingress/injection switch setting from another model as a substitute.
2. **One NIC and local console:** sufficient for short capture qualification. While on P5, use local commands. Stop capture before moving the same cable to ordinary P4 for updates/export. This temporarily stops observation. Without continuing NTP/management, do not treat a two-week unattended run as fully qualified.
3. **Separate management adapter later:** retain enp1s0 on P5 and connect a supported USB Ethernet adapter to ordinary P4. Use that added interface only for management. It is not necessary to make the t530 an inline bridge. This is the preferred separation for unattended use if shared-port management is unavailable.

If there is neither a local console nor a verified management path, stop before moving the cable/enabling a dedicated mirror destination. The guide does not reconfigure Netplan, set a default gateway to the t530 or enable forwarding/NAT. Those operations would describe a different deployment.

## Session 2 — Wire and migrate without breaking the old network

1. Back up the switch/AP settings through their documented administration interfaces. Record model, hardware revision and firmware privately. Leave the original ZTE configuration recoverable.
2. Connect ZTE LAN to P1. Connect PC to P3. Leave t530 temporarily on ordinary P4. Keep only one intended cable uplink from the AP; do not make a switching loop.
3. Configure the separate AP in its documented bridge/AP mode and connect its uplink to P2. Use a distinct temporary SSID so you can tell which radio serves each phone. Preserve encryption and a strong private passphrase. Disable a spare router's DHCP server if its AP procedure requires it; the ZTE remains the address authority.
4. After an AP reboot, allow 2–5 minutes, then test the PC's Internet connectivity. Do not advance solely because a timer expired.
5. Move one phone to the new SSID. Allow 30–60 seconds for association/DHCP. Verify normal browsing and that its client address belongs to the intended home network. Repeat for the other phones. Record private per-SSID MACs/addresses and UTC times. Do not disable private-MAC features merely to simplify profiling.
6. Once all intended devices work, prevent reconnection to the old ZTE SSID as described in Session 0. Leave modem/DHCP/NAT functions intact. Recheck the PC and phones for two minutes.

The following PC commands identify the actual Ethernet/IPv4 configuration; they do not assign static addresses:

```powershell
Get-NetIPConfiguration
Get-NetIPAddress -AddressFamily IPv4 | Where-Object AddressState -eq Preferred
```

Only the switch/AP vendor can supply exact UI/CLI names for the hardware you choose. The complete logical port settings are below; do not paste Cisco/TP-Link CLI commands into the ZTE or an unrelated switch.

## Session 3 — Configure the mirror once, then prove access

Set these values in the switch's mirroring configuration and save the configuration persistently:

| Setting | Value in the five-port example |
| --- | --- |
| Mirroring/session state | Enabled |
| Destination / monitor / mirroring port | P5 only |
| Source / monitored / mirrored ports | P1, P2, P3, plus each additional ordinary port carrying a monitored endpoint |
| Direction on each selected source | Ingress / RX / received only |
| Egress / TX on those sources | Disabled |
| P5 as a source | Disabled; never mirror the destination back into itself |
| P4 | Ordinary recovery/management port; add RX only if its traffic is intentionally in capture scope |

Here ingress means a frame entering the switch from the router/AP/PC. Selecting all relevant sources RX-only obtains each traversal's incoming frame without also copying its departure at another selected port. For example, phone request enters P2 and PC response enters P3. Router-to-phone reply enters P1. Mirroring P1 and P2/P3 in both directions can count the same packet twice and distort rates; this collector does not transparently deduplicate mirror copies. [Duplicate-copy discussion](https://www.keysight.com/nl/en/assets/3120-1089/white-papers/Duplicate-Packets-Are-They-Good-or-Bad-and-Best-Practices-for-Managing-Them.pdf)

If the switch cannot implement this source/direction combination, stop and adapt the observation design for that exact model. Merely mirroring the router uplink both ways covers its crossing traffic but may miss phone-to-PC paths. Mirroring AP and PC ports both ways is not an equivalent substitute because their shared traffic may be duplicated. A Gigabit destination can also be oversubscribed by aggregate sources; inspect switch counters and compare independently generated low-rate tests before loading it.

Move enp1s0 to P5 with the t530 local console available. Allow about 30 seconds for link establishment, then on t530:

```bash
ip -br link show enp1s0
ip -br addr show enp1s0
timedatectl status
```

For the shared-port management option, test actual reachability while mirroring is active. An old assigned address remaining on the interface is insufficient. Read the current address locally, then from Windows:

```powershell
$sensorAddress = Read-Host 'Current t530 management IPv4 address'
Test-NetConnection -ComputerName $sensorAddress -Port 22
```

On t530, test current gateway reachability and name resolution, then inspect NTP:

```bash
DEFAULT_GW=$(ip -4 route show default dev enp1s0 | awk 'NR==1 {print $3}')
if [ -n "$DEFAULT_GW" ]; then
  ping -c 3 -W 2 "$DEFAULT_GW"
fi
getent ahostsv4 ubuntu.com
timedatectl timesync-status
```

If this fails after moving to P5, use the local-console option for short sessions and stop expecting remote SSH/dashboard through that port. The switch may deliberately isolate the destination. Do not flush addresses, disable host firewalls or reboot the ZTE to fix a designed port limitation. To recover, stop capture locally, move the same cable back to P4, allow 30–60 seconds and check DHCP/clock again. A long-run management adapter or explicitly supported shared-port design is required before Session 9's unattended gate.

With shared mirror/management, also compare the sensor's own control traffic: some implementations can deliver both an ordinary and a mirrored copy. Infrastructure/sensor subjects are not automatically excluded by this collector. Keep them identified separately during offline household-baseline review; do not assume all observed local addresses represent a phone or PC. A separate management interface remains easier to qualify.

## Session 4 — Prove each phone reaches the wired PC and the sensor

On Windows, open an **Administrator PowerShell** for the short-lived probe server and narrowly scoped inbound rule. The rule accepts TCP 8088 only at the entered PC address and only from the entered phones. This does not disable the Windows firewall:

```powershell
$probeDir = Join-Path $env:TEMP ('apf-probe-' + [guid]::NewGuid().ToString('N'))
New-Item -ItemType Directory -Path $probeDir | Out-Null
Set-Content -LiteralPath (Join-Path $probeDir 'probe.txt') -Value 'Adaptive IPS framework visibility probe'
$pcAddress = Read-Host 'Wired PC LAN IPv4 address'
$phoneAddresses = (Read-Host 'Three phone IPv4 addresses, comma-separated').Split(',') | ForEach-Object { $_.Trim() }
$probeRule = 'APF-Probe-' + [guid]::NewGuid().ToString('N')
New-NetFirewallRule -Name $probeRule -DisplayName $probeRule -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8088 -LocalAddress $pcAddress -RemoteAddress $phoneAddresses -Profile Any | Out-Null
python -u -m http.server 8088 --bind $pcAddress --directory $probeDir
```

If a corporate policy refuses the narrow rule, resolve that endpoint policy rather than disabling protections. Keep this terminal open while testing. Serving only the generated directory avoids exposing personal project files.

On t530, test one phone at a time:

```bash
read -r -p 'Wired PC LAN IPv4 address: ' PC_IP
read -r -p 'Phone under test IPv4 address: ' PHONE_IP
date -u --iso-8601=seconds
sudo timeout --signal=INT 60 tcpdump -i enp1s0 -nn -e -tttt -S -s 128 \
  "host $PC_IP and host $PHONE_IP and tcp port 8088"
```

During those 60 seconds, open http://PC-ADDRESS:8088/probe.txt?probe=phone1-test1 on that phone, replacing PC-ADDRESS with the entered address. Request it three times about five seconds apart, changing the final test number to prevent a cached response. The phone must display the probe. The PC terminal should record its requests. The t530 must show phone-to-PC and PC-to-phone packets at corresponding times. The timeout normally returns 124 when its minute ends; tcpdump prints its capture/drop summary. This bounded display is not a household payload archive.

Repeat a fresh 60-second capture for phone2 and phone3 with their actual addresses. Keep a private ledger: alias, SSID, source/target addresses, request success, both observed directions, UTC time, counts and mirror configuration. If the fetch succeeds but sensor frames are missing, the observation path fails. If the fetch fails too, investigate the server, PC firewall, AP isolation and routing before judging the mirror. Repeated identical sequence ranges need comparison with endpoint evidence; legitimate TCP retransmissions must not be mistaken automatically for mirror duplicates.

After the last probe, press Ctrl+C in the PC server terminal, then clean up the exact temporary rule and generated files in that same PowerShell session:

```powershell
Remove-NetFirewallRule -Name $probeRule
Remove-Item -LiteralPath (Join-Path $probeDir 'probe.txt')
Remove-Item -LiteralPath $probeDir
```

No phone-to-phone coverage is established by this test. If desired, test a separately owned service between wireless endpoints and record whether its traffic reaches the AP uplink; absence must remain a declared blind path.

## Session 5 — Check Internet traffic, IPv6 and per-device identity

For each phone and the PC, run a 60-second capture while that device alone starts a known normal browsing/streaming action. A per-device MAC filter includes both IP families when the bridged path preserves that MAC:

```bash
read -r -p 'Observed current device MAC on this AP/LAN: ' DEVICE_MAC
sudo timeout --signal=INT 60 tcpdump -i enp1s0 -nn -e -s 128 \
  "ether host $DEVICE_MAC and (ip or ip6)"
```

Record outbound device IPs and matching inbound traffic, distinguishing background connections from the known activity. Confirm actual packet source/MAC behavior rather than assuming all AP modes preserve identity. If every phone appears only as the AP's upstream IP/MAC, investigate AP NAT/proxy behavior before building per-device profiles. Seeing DHCP or broadcast alone is insufficient. On an actual bridged AP, LAN-side Internet observations should retain the clients' internal IPs; the ZTE's public translation is beyond this mirror.

If IPv6 client traffic is present, record its actual local prefix(es) privately. Rebuild LAN_ARGS with those prefixes and use them consistently in preflight, foreground capture and service configuration. If you cannot determine them yet, record IPv6 as unqualified and pause the whole-home collection claim; do not label missed IPv6 observations benign. Link-local and globally routed prefixes are different scopes. Phone privacy-address changes and DHCP renewals require time-bound identity review, not permanent assumptions about an address.

In the same collector window, update the optional confirmed prefix before creating the qualification directories:

```bash
read -r -p 'Confirmed local IPv6 CIDR, or empty if none present: ' LAN6_CIDR
LAN_ARGS=(--lan "$LAN_CIDR")
if [ -n "$LAN6_CIDR" ]; then
  LAN_ARGS+=(--lan "$LAN6_CIDR")
fi
```

The scope is qualifying the stated paths, not claiming all network/radio/Internet events. If a phone remains on cellular data, a VPN changes application visibility or an AP switches a peer flow locally, record that exception. Ordinary metadata does not reveal encrypted web payloads.

Do not turn its booleans true merely to obtain exit 0. Resolve operational FAIL first; review optional dependency, clock and observation issues explicitly.

Run for ten minutes, generating the known PC/phone activities in the table:

```bash
sudo timeout --signal=INT --kill-after=30s 10m \
```

| Capture minute | Activity |
| --- | --- |
| 0–2 | Keep devices connected and otherwise idle; record background traffic. |

| 4–6 | Phone1 browsing/streaming. |

In a second tmux window during capture, local status works even without mirror-port SSH:

```bash
curl -fsS http://127.0.0.1:8081/ips/metrics | python3 -m json.tool
```

## Session 7 — Twenty-minute metadata qualification

Select the extra parsers deliberately. --metadata measures supported UDP DNS and complete one-packet TLS ClientHello metadata; --http measures supported complete cleartext HTTP/1 request headers. It stores reduced features, not a full household packet/payload archive. This does not inspect HTTPS content, reconstruct TCP streams or parse QUIC applications. Ordinary HTTPS-heavy use may yield zero HTTP parses; DoH/DoT and split ClientHellos can limit metadata.

```bash
sudo .venv/bin/python scripts/home_preflight.py \
  --interface "$SENSOR_IFACE" "${LAN_ARGS[@]}" --metadata --http \
  --data-dir /var/lib/apf/metadata-qualification
sudo timeout --signal=INT --kill-after=30s 20m \
  .venv/bin/python Controller/home_sensor.py \
  --interface "$SENSOR_IFACE" "${LAN_ARGS[@]}" --metadata --http \
  --data-dir /var/lib/apf/metadata-qualification
```

During these twenty minutes, spend about five minutes each on PC activity and the three phones. Include the owned HTTP probe again if testing HTTP lexical collection; repeat the temporary server/rule setup and cleanup. Compare DNS/TLS evidence with the known transaction where possible rather than assuming every encrypted application is observable.

After shutdown:

```bash
sudo .venv/bin/python scripts/audit_home_data.py /var/lib/apf/metadata-qualification
```

Inspect parser_settings, per-device counts, partial/held windows, source provenance and parse/loss/cap counters. Parse failures require review; zero successful parses have several possible causes. This separate directory prevents silently mixing header and metadata feature contracts. Never feed these site-v3 rows to the shipped legacy v2 RF/AE bundles.

Proceed after short checks pass and a sustainable management/NTP path exists. ### Prepare reviewable inventory before the long run

The short captures may legitimately run without inventory and produce HOLD evidence. If you want the later explicit baseline-review command to approve descriptive profiles, configure its shadow inventory **before** this longer run. It cannot retrospectively turn old no-policy records into records from a new approved policy. Pure observation-only collection remains useful, but all candidate eligibility remains held without the required policy/identity/quality evidence.

Create a root-controlled file readable by the service account. The example is copied only if no private policy already exists:

```bash
if ! sudo test -e /etc/apf/site-policy.json; then
  sudo install -o root -g apf -m 640 /opt/apf/Controller/site_policy.example.json /etc/apf/site-policy.json
```

## Session 9 — Fourteen-day initial collection and daily review

After the first 24-hour gate, continue for an initial fourteen-day operating cycle. Extend for missing workflows or inactive devices. ## Rollback and what to report

For network disruption, stop apf-home if running, restore the saved switch mirror configuration, reconnect the PC/t530 to the original ordinary LAN ports, and reconnect phones to the original ZTE Wi-Fi. Keep only one AP uplink and avoid loops. Restore only settings you deliberately changed; do not factory-reset the ISP router. Allow 30–60 seconds for wired/DHCP recovery and 2–5 minutes for a device reboot when required, checking actual connectivity each time. Preserve collected files for analysis.

| Checkpoint | Record privately |
| --- | --- |
| Equipment | Switch/AP model, hardware revision, firmware, port map and AP bridge mode. |
| Management | Shared-port behavior actually tested, or dedicated management/local-console limits; NTP/reboot/SSH results. |
| Observation | Each phone/PC request/response and Internet/address-family result; duplicates, loss, NAT/proxy identity and same-AP bypasses. |
| Data | Short/one-hour/day audit output, source/schema fingerprints, parser settings and resource/file growth. |
| Baseline | Device/workflow participation, unknown/held intervals and private activity references; no automatic benign labels. |

If no extra observation hardware is available today, the useful immediate outcome is Session 1's offline qualification plus an explicitly limited test of the t530's own/broadcast traffic. It cannot substitute for collecting the other devices. The next hardware choice is a verified mirror switch and bridged AP, with a management method selected before an unattended run. Native H188A mirror support remains a possible alternative only after the actual ISP firmware and LAN/WLAN paths are proven.
