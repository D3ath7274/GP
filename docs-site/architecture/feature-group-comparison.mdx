This note explains where each behavioral feature group can add more useful evidence than a simpler alternative. It is a design rationale, not measured superiority over a vendor, model or detector. A stronger claim requires matched experiments at the same false-alert/action budget. The editable presentation includes a dedicated slide for every G1–G24 group and fuller speaker notes with code evidence and primary references.

## Current scope

The legacy reference retains 102 columns; the separate site collector has 71 columns. Counts include identifiers/audit fields, not only predictors. G18–G24 remain planned. Existing site measurements and offline diagnostics do not establish a trained production attack model or a qualified automatic firewall loop. The [method inventory](/architecture/feature-methods) records exact recommended computations and current limits, while the [rationale](/architecture/feature-rationale) records benign controls and qualification needs.

## Comparison by group

| Group | Alternative and added value | Important limit |
| --- | --- | --- |
| G1: Timing and burst rhythm | Mean PPS alone: Distinguishes schedules that have the same average volume. Payload matching alone: Adds timing evidence when application content is encrypted. | Site exports three timing summaries. Burst detection is a legacy heuristic. |
| G2: Directionality and asymmetry | Outgoing volume alone: Shows whether the destination also makes observable progress. One fixed rate threshold: Adds context for downloads, uploads and one-way pressure. | Legacy reverse aggregates pool IP pairs and protocol. Exact session matching is still needed. |
| G3: TCP lifecycle proxies | Counting SYN packets: Separates attempts from actual protocol progress. Five-second volume only: Can represent stalled or incomplete activity across windows when state exists. | Current legacy values are window proxies. Persistent sequence-aware TCP state is planned. |
| G4: Distribution entropy | Unique-value counts: Distinguishes a dominant category from an even distribution with the same richness. Numeric port variance: Treats service identifiers as categories rather than meaningful distances. | Legacy length entropy describes captured frame sizes. Entropy alone is not a verdict. |
| G5: ARP binding behavior | IP flow features alone: Adds visibility into an IPv4 link-layer mechanism outside IP sessions. ARP reply volume alone: Can distinguish a conflicting claim from ordinary address-resolution activity. | Legacy heuristics and DAI checks remain. Trusted bindings and IPv6 NDP need more integration. |
| G6: Packet-size distribution | Average size alone: Separates constant-size traffic from mixed sizes with the same mean. Min/max range alone: Uses the distribution rather than only its extreme observations. | Site size SD exists. Variance duplicates SD information and should be tested by ablation. |
| G7: Port-use structure | A single flow row: Adds source-wide exploration across destinations and services. One port number or port count: Adds concentration and service context to explain the same count. | The legacy sorted-port score measures density, not arrival order or a specific scanner. |
| G8: Broadcast and multicast context | One global rate threshold: Explains discovery bursts without raising thresholds for every workload. Ignoring local discovery: Preserves evidence about address resolution and potentially harmful storms. | Legacy network ratios exist. The site collector does not reproduce the entire set. |
| G9: Flow creation pressure | Bandwidth thresholds: Adds state-creation pressure that can occur at modest byte volume. Packet count alone: Separates repeated use of existing keys from many newly created keys. | Legacy flows_per_window is a key-count proxy. It does not measure actual table occupancy. |
| G10: Audit metadata and provenance | A dataset without provenance: Supports replay, diagnosis and valid comparisons across collection conditions. Feeding tool names into a model: Keeps evaluation focused on behavior rather than experiment identifiers. | Audit-only by design. These fields support eligibility and review, not maliciousness votes. |
| G11: Reconnaissance evidence | A SYN-flood rule alone: Adds several probe styles and exploration across hosts or services. A known scanner signature: Describes reconnaissance behavior that may persist across tool changes. | Site counters exist. Resets and unreachables are summaries, not matched-probe proof. |
| G12: Header and evasion evidence | Rate and port features only: Adds changes in protocol/header behavior at the same traffic volume. Static device fingerprint alone: Can compare a device’s new observations with its own prior context. | Site summaries exist. Scaled-window interpretation and fragment reassembly remain incomplete. |
| G13: Long-horizon contacts | Five-second windows alone: Retains slow exploration and repeated behavior spread across windows. Unbounded connection history: Uses declared horizons and caps to fit constrained hardware. | Site values use minute buckets. Current CV describes contact windows, not packet-level beacons. |
| G14: Service initiation behavior | Aggregate volume only: Distinguishes how traffic approaches services and whether the workload changes. Port labels alone: Adds initiation frequency and transfer context around a service category. | Current site fields are proxies. Authentication outcomes and exact sessions need other evidence. |
| G15: DNS metadata | Destination IP reputation alone: Adds behavior of name generation and DNS response outcomes. Domain blocklists alone: Can expose changing name patterns without a previously listed domain. | Single-question UDP parsing exists. Exact transactions, TCP DNS and encrypted DNS need more support. |
| G16: TLS and QUIC evidence | Payload inspection without keys: Can retain limited visible handshake evidence under encryption. A fingerprint blocklist alone: Adds device-relative novelty and parser/visibility context. | Current first-packet custom hashes are not JA4. QUIC and broader reassembly remain work. |
| G17: HTTP behavior and lexical evidence | Transport statistics alone: Adds request structure that volume and TCP flags cannot describe. One literal payload string: Can support investigation of changed encoding or request patterns. | Single-packet HTTP/1 summaries exist. They do not prove injection, authorization abuse or exploit success. |
| G18: Resource and state exhaustion | Bandwidth or PPS only: Would observe state or resource pressure even when bandwidth is modest. Connection counts alone: Would connect demand to measured capacity and useful progress. | Planned. Actual queue, capacity and progress telemetry are not installed as this group. |
| G19: Identity conflict and reassignment | A permanent IP identity: Would handle address reuse instead of inheriting another device’s profile. First-seen MAC learning: Would compare claims with independent, time-valid identity evidence. | Planned beyond current manual inventory consistency. IP/MAC agreement is not authentication. |
| G20: Management and SD-WAN control plane | User data-plane statistics alone: Would add direct evidence about control sessions and configuration changes. Static configuration review: Would retain timing and outcomes around live changes or repeated failures. | Planned. Requires supported, authenticated router or SD-WAN telemetry. |
| G21: Credential abuse and lateral transitions | Authentication-port counts: Would distinguish repeated failure, successful use and unauthorized transitions. Independent isolated alerts: Would retain the identity/time sequence across hosts and services. | Planned. Port summaries do not provide authentication results or trusted user identity. |
| G22: Application authorization abuse | Network rate and session features: Would inspect the meaning of low-volume application actions. Payload signatures alone: Would evaluate whether this identity may access this resource in this state. | Planned. Needs application/identity integration and authorized plaintext or audit visibility. |
| G23: Command-and-control and exfiltration | One periodicity threshold: Would combine timing with role, destination and protocol context. A static destination list: Would support changing infrastructure and slow behavioral changes. | Planned comprehensive group. Existing G13/G15/G16 measurements are smaller foundations. |
| G24: Exploitation outcome evidence | An unusual payload or anomaly score: Would distinguish a suspicious attempt from observed target impact. A signature alert alone: Would add independent evidence of what happened after the alert. | Planned. Requires isolated target/application/endpoint evidence and causal review. |

## Use the comparisons responsibly

Device history, network context, provenance/independent labels, observation quality and policy context support all numbered groups. They explain whether an unusual value is meaningful and whether it can be attributed to the right device or rule. Metadata and detector labels should not become shortcuts for training attack predictors.

The current [offline group tool](/deployment/feature-evidence) uses frozen marginal/reference ranks, separately calibrated group/global maxima and insufficient-evidence outcomes. It does not learn joint causal attack chains, prove maliciousness or update firewall rules. Signature engines, stateful analysis, learned interactions and application/outcome telemetry answer complementary questions. Current industry products can combine these methods too; the deck claims no exclusive capability or industry-wide advantage.

Measure each group's added yield through removal/retraining, later-time/device/tool/site tests, matched benign workloads, false alerts per device-day, missed/abstained coverage, delay and capture/resource cost. For response claims, independently verify containment and innocent-client continuity. Follow [the campaign guide](/deployment/security-campaigns) and [delivery gates](/roadmap/delivery-phases). The next pilot step remains [software qualification](/deployment/no-mirror-pilot), not enabling a new live detector from this presentation.
