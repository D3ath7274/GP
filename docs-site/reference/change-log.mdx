## 2026-11-08 · Parse errors from chance matches in encrypted data

The first replay of a video-streaming session with the fixed decoder reported 4 `tls_parse_errors`. A frame scan of that session and the three Siege hours found that every TLS and HTTP parse error in them was an incoming segment from TCP port 443 in the middle of an encrypted stream. `client_hello()` accepted any payload with `0x16` first and `0x01` at offset 5, which random bytes match about once per 65,536 segments; their record-version bytes were random. The HTTP check flagged any unterminated payload that began with 3–12 capital letters and a space, about once per 220,000 segments. Parse errors are run-latched quality faults. Chance matches would therefore have held almost every long live run from baseline approval for reasons unrelated to measurement quality.

A TLS candidate now needs a record version from 3.0 to 3.4. An unterminated payload counts as an HTTP parse error only with request-line evidence: a target starting with `/` or `http(s)://`, `OPTIONS *`, `CONNECT host:port`, or a complete ` HTTP/1.x` request line. A first draft also accepted `*` after any token; two of the observed encrypted segments began that way, so the asterisk form is limited to OPTIONS. Real ClientHellos and complete requests take the same path as before, so G16 and G17 values are unchanged. For that reason the collection contract and schema hash are unchanged too, and existing directories continue. Truncated real ClientHellos and plausible unterminated requests still count as errors. Two regression tests, built from bytes observed in the pilot, fail on the previous decoder.

Operator impact: replays and live runs no longer accumulate these chance parse errors. Earlier replay reports keep their recorded counts. The [explainer](/developers/pilot-explained) adds this as a second worked example, and the [pilot page](/deployment/no-mirror-pilot) records the video-streaming session. Collection and feature-method pages describe the stricter tests. S10 and S68 stay Partial. Verification is recorded in DOCUMENTATION_VALIDATION.md.

## 2026-11-08 · Offloaded IPv4 frames and retried ClientHellos in the site decoder

Stage D endpoint replays exposed two silent measurement gaps in `Controller/site_features.py`. Both were found by reconciling sensor counts with tshark for four gaming captures. First, Windows large-send offload hands the capture point outgoing super-segments whose IPv4 total length is 0. `decode()` trusted that 0 and treated the payload as empty, so those frames added nothing to `g14_out_payload_bytes` and their ClientHellos never reached G16. These were the large ClientHellos, consistent with post-quantum key shares, and no counter recorded the loss. Second, `client_hello()` checked only the first TLS record, so it skipped a ClientHello sent after a TLS 1.3 compatibility ChangeCipherSpec record, which is how a HelloRetryRequest retry is sent. Together the two gaps hid 18–27% of TCP ClientHellos in the [pilot sessions](/deployment/no-mirror-pilot).

For an IPv4 total length of 0, the decoder now uses the captured datagram, provided the snap length kept the frame whole and the frame is longer than the 60-byte Ethernet minimum plus 4 bytes per VLAN tag. This way padding never becomes payload. Each such frame increments the new `ipv4_zero_length_frames` health counter. The collection report lists the counter, and the shadow policy treats it as a run-latched quality fault: windows stay held and baseline review refuses the run, because a wire or mirror port should not carry such frames. `client_hello()` skips exactly one compatibility ChangeCipherSpec record, so a retry counts as a second ClientHello. QUIC ClientHellos remain outside G16.

The collection contract gains a `decoder` entry. As a result, schema.json and `collection_schema_sha256` change, while the 71 columns stay the same. Operator impact: directories and approved profiles created by earlier code are refused, so start a new data directory. Re-replay stored endpoint captures before using their G14 payload or G16 values. The no-mirror runbook and pilot page note the expected counter for endpoint replays and record the Stage D progress. Their guide version, and the results template's, is now 2026-11-08. The [feature rationale](/architecture/feature-rationale) for G14 and G16, the [feature methods](/architecture/feature-methods), the [collection](/deployment/home-collection) and [shadow-policy](/security/shadow-policy) pages and the AI handoff were updated.
